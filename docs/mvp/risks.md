## Detailed Risks

### R-001: Непонятная обратная связь

**Описание:** Игрок не понимает, почему получил такую оценку, что приводит к фрустрации.

**Причины:**
- Слишком технические сообщения о нарушениях
- Отсутствие конкретных рекомендаций
- Неочевидная связь между предметами и оценкой

**Влияние:** Игроки бросают игру, не понимая как улучшить результат.

**Вероятность:** Средняя

**Стратегия митигации:**
- Использовать простой язык без терминов
- Давать конкретные рекомендации ("Добавьте больше деревянных предметов")
- Показывать визуальную индикацию нарушений
- Тестировать обратную связь на реальных игроках

**Триггеры:**
- Игроки спрашивают "почему такая оценка?"
- Низкие рейтинги в тестах
- Много повторных попыток без улучшения

**Ответственный:** Product Owner + UX Designer

---

### R-002: Слишком простая оценка

**Описание:** Оценка не различает хорошие и плохие расстановки достаточно хорошо.

**Причины:**
- Недостаточно ограничений
- Слишком широкие пороги
- Векторы предметов не отражают стиль

**Влияние:** Игра становится скучной, нет чувства достижения.

**Вероятность:** Средняя

**Стратегия митигации:**
- Начать с 3-5 ограничений, добавить больше при необходимости
- Калибровать пороги на тестовых данных
- Использовать golden tests для проверки дифференциации
- Собрать фидбек от тестеров

**Триггеры:**
- Все расстановки получают одинаковую оценку
- Игроки замечают паттерн оценки
- Low replayability

**Ответственный:** Game Designer

---

### R-003: Технические проблемы производительности

**Описание:** Низкий FPS, лаги при взаимодействии с предметами.

**Причины:**
- Неоптимальный рендеринг Three.js
- Слишком много полигонов в предметах
- Частые пересчёты векторов

**Влияние:** Игроки испытывают дискомфорт, могут отказаться от игры.

**Вероятность:** Низкая

**Стратегия митигации:**
- Профилировать производительность рано
- Использовать LOD для предметов
- Кэшировать вычисления векторов
- Ограничить количество одновременных предметов

**Триггеры:**
- FPS < 30 на целевых устройствах
- Жалобы на лаги
- Высокое использование памяти

**Ответственный:** Technical Lead

---

### R-004: Недостаточно предметов для теста

**Описание:** 5-10 предметов недостаточно для meaningful тестирования гипотезы.

**Причины:**
- Слишком маленький каталог
- Предметы слишком похожи
- Нет разнообразия векторов

**Влияние:** Невозможно проверить гипотезу о геймплее.

**Вероятность:** Низкая

**Стратегия митигации:**
- Подготовить 10 предметов с разнообразными векторами
- Убедиться, что предметы покрывают диапазон признаков
- Быть готовым добавить предметы быстро

**Триггеры:**
- Игроки отмечают недостаток выбора
- Невозможно создать интересные расстановки
- Векторы кластеризуются

**Ответственный:** Content Designer

---

### R-005: Нарушение архитектуры под давлением сроков

**Описание:** Команда начинает писать код без тестов, нарушать слои DDD.

**Причины:**
- Давление дедлайна
- Недостаточное понимание архитектуры
- Искушение "быстро поправить"

**Влияние:** Технический долг, сложность поддержки, баги.

**Вероятность:** Средняя

**Стратегия митигации:**
- Строго следовать процессу (docs → slice → TDD → code)
- Проводить architecture review
- Автоматизировать проверку зависимостей
- Напоминать о Definition of Done

**Триггеры:**
- Код без тестов
- Domain импортирует Infrastructure
- Появление God objects
- Diff вместо полных файлов

**Ответственный:** Tech Lead + Architect

---

### R-006: Scope Creep

**Описание:** Постепенное добавление функций вне MVP.

**Причины:**
- "А давайте ещё добавим..."
- Фидбек от стейкхолдеров
- Искушение сделать "полноценную игру"

**Влияние:** Срыв сроков, размытие фокуса, невыполненный MVP.

**Вероятность:** Высокая

**Стратегия митигации:**
- Чёткий документ Out of Scope
- Reference к MVP Charter
- Откладывать идеи в backlog post-MVP
- Регулярно проверять scope на встречах

**Триггеры:**
- Обсуждение функций из Out of Scope
- Запросы на "просто маленькую фичу"
- Упоминание экономики, прогрессии, мультиплеера

**Ответственный:** Product Owner

---

### R-007: Отсутствие детерминизма в тестах

**Описание:** Тесты дают разные результаты при одинаковых входных данных.

**Причины:**
- Использование случайности без seed
- Зависимость от времени
- Глобальное состояние между тестами

**Влияние:** Невозможно доверять тестам, баги пропускаются.

**Вероятность:** Средняя

**Стратегия митигации:**
- Использовать deterministic RNG с seed
- Изолировать тесты друг от друга
- Избегать глобального состояния
- Проверять тесты на воспроизводимость

**Триггеры:**
- Тесты иногда проходят, иногда нет
- Разные результаты на разных машинах
- Зависимость от порядка запуска тестов

**Ответственный:** QA Lead

---

### R-008: Недостаточное покрытие тестами

**Описание:** Критическая логика не покрыта тестами.

**Причины:**
- Нехватка времени
- Сложность тестирования
- Незнание TDD

**Влияние:** Баги в production, регрессии.

**Вероятность:** Средняя

**Стратегия митигации:**
- Требовать тесты в Definition of Done
- Pair programming для TDD
- Автоматизировать запуск тестов в CI
- Monitor coverage метрики

**Триггеры:**
- Coverage < 90% для Domain
- Критические функции без тестов
- Ручное тестирование вместо автоматического

**Ответственный:** QA Lead

## Risk Monitoring

### Weekly Review
- Проверять статус всех рисков
- Обновлять вероятность и влияние
- Идентифицировать новые риски
- Оценивать эффективность митигации

### Risk Triggers Dashboard
- Мониторить триггеры рисков
- Эскалировать при активации триггеров
- Документировать инциденты

## Contingency Plans

### Если R-001 активируется:
1. Срочно протестировать обратную связь на 5 игроках
2. Переписать сообщения на основе фидбека
3. Добавить визуальные подсказки

### Если R-005 активируется:
1. Остановить разработку
2. Провести architecture review
3. Выделить время на рефакторинг
4. Обновить документы

### Если R-006 активируется:
1. Напомнить о MVP Charter
2. Переместить фичи в post-MVP backlog
3. Получить явное подтверждение scope от PO
